# バージョンポリシー

**位置づけ**: 2類責務別ポリシー
**責務**: バージョン表記、累積方式、Major / Minor 更新条件
**ステータス**: 初期策定

---

## 1. バージョン表記

本プロジェクトの正式バージョンは、以下の形式で表記する。

```text
v.{Major}.{Minor}
```

未安定版の例:

```text
v.0.1
v.0.12
```

安定版リリース系列の例:

```text
v.1.13
v.2.23
v.12.150
```

## 2. 累積方式

初回安定版リリース前の正式バージョンは、`v.0.{Minor}` として扱う。

初回安定版リリース前は、Phase が進んでも `Major` を `0` のまま維持する。

`Major` は安定版リリース系列を表す。

`Minor` はプロジェクト全体で累積する変更番号として扱う。

フェーズ番号と `Minor` は、いずれもリセットしてはならない。

`Major` は初回安定版リリースで `1` へ進める。以後の安定版リリース系列更新時も、過去の値へ戻してはならない。

## 3. Major の扱い

Major バージョンは安定版リリースの扱いである。

`Major` が `0` の間は、安定版未リリースの開発・検証段階である。

`Major` が `1` 以上のバージョンは、安定版リリース系列として扱う。

初回安定版リリースは、Phase 7、Phase 17、Phase 27 のような 7系フェーズをデフォルト方針とする。

5系フェーズは設計・デザイン改良、仕様整理のためのフェーズとし、安定版リリースフェーズまたは補助的なリリース判定フェーズとして扱わない。

6系フェーズは、大規模なバグ修正とドキュメント整合性向上をデフォルト方針とする安定版リリース準備フェーズとする。必要に応じて移行準備と検証強化も行う。6系フェーズ自体は安定版リリースフェーズとして扱わない。

Phase 9 は、ユーザー承認に基づく安定版判定フェーズとして扱う。Phase 19、Phase 29 のような後続9系フェーズは、自動的な安定版判定フェーズまたは補助的なリリース判定フェーズとして扱わない。後続9系フェーズで安定版判定を行う場合は、マスター開発計画と2類ポリシーに明記し、ユーザー承認を得る。

## 4. Minor の更新条件

以下のいずれかに該当する場合、`Minor` を更新する。

- 後方互換を維持した機能追加
- 既存機能の機能改良
- バグ修正
- セキュリティ修正
- ドキュメント更新
- テスト追加、検証修正
- 既存仕様を変えない内部整理
- CI/CD、開発環境、リリース手順の修正
