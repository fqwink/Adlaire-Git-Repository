# バージョンポリシー

**位置づけ**: 2類責務別ポリシー
**責務**: 開発版バージョン、安定版バージョン、累積方式、リセット禁止
**ステータス**: Adlaire Portal System 方式適用

---

## 1. 基本方針

本プロジェクトは、Adlaire Portal System のバージョンポリシーを採用し、本リポジトリの既存表記に合わせて `v.` prefix を維持した形式へ適用する。

本プロジェクトは、**開発版バージョン** と **安定版バージョン** の2種類のバージョン番号を持つ。

どちらも、重大度、破壊的変更、軽微な修正、機能追加、バグ修正、ドキュメント改訂などの変更種別によって桁や増分を使い分けない。

バージョンは単純な積み上げ式の累積連番とし、いかなる理由があってもリセット、巻き戻し、1からの数え直しをしてはならない。

## 2. 開発版バージョン

開発版バージョンは、仕様、タスク管理、実装、テスト、検証、ドキュメント整合性など、リポジトリへ変更を加える開発上の改訂単位に付与する番号である。

開発版バージョンは、以下の形式で表記する。

```text
v.0.N
```

`0` は開発版を表す固定値である。

`N` は開発版の累積変更番号であり、1から始まり、変更単位ごとに1ずつ増やす。

`N` は安定版リリース後もリセットしてはならない。桁揃え、ゼロ埋め、重大度別の増分変更も行わない。

開発版バージョンの例:

```text
v.0.1
v.0.12
v.0.49
```

## 3. 安定版バージョン

安定版バージョンは、開発版バージョンの中から、リリースポリシーに基づき安定版として切り出した時点に付与する番号である。

安定版バージョンは、以下の形式で表記する。

```text
v.X.Y
```

`X` は安定版リリースの通し番号である。初回安定版リリースを `1`、2回目を `2` とし、安定版リリースごとに1ずつ増やす。

`Y` は、その安定版を切り出した時点の開発版バージョン `v.0.N` の `N` である。

`X` と `Y` はいずれもリセットしてはならない。同一の安定版リリースの中で、`X` が指すリリース回数と `Y` が指す開発版時点をずらしてはならない。

安定版バージョンの例:

```text
v.1.8
v.2.10
v.3.49
v.12.150
```

たとえば、開発版 `v.0.49` の時点を3回目の安定版として切り出す場合、安定版バージョンは `v.3.49` とする。

## 4. 表記互換と旧方針の扱い

本プロジェクトでは、`v.` prefix を維持する。Adlaire Portal System の `v0.N` / `vX.Y` 表記は、本リポジトリでは `v.0.N` / `v.X.Y` として適用する。

旧方針で記録済みの `v.1.x`、`v.2.x` 形式の開発・文書改訂履歴は、移行前履歴として保持する。過去履歴を後から全面改番してはならない。

移行後の開発版バージョンは、既存の開発版累積番号の最大値から継続する。開発版 `v.0.50` に続く本改訂の文書バージョンは `v.0.51` とする。

旧方針における `Major` / `Minor` という呼称は、移行後の正式な要素名として使用しない。必要な場合は、開発版の `N`、安定版リリース通し番号の `X`、安定版切り出し時点の開発版番号の `Y` として説明する。

## 5. タスク管理との関係

今後の作業管理は、フェーズ単位ではなく `docs/tasks/TASK_MANAGEMENT.md` のタスク単位で行う。

タスク管理ファイルは、開発版バージョンまたは安定版バージョンを自動的に決定する文書ではない。

開発版バージョンは、承認済み変更単位ごとに累積して更新する。

安定版バージョンは、リリースポリシーに基づき、安定版リリースタスクとしてユーザー承認された場合のみ更新する。

## 6. 開発版バージョンの更新条件

以下のいずれかに該当する場合、開発版バージョンの `N` を1つ進める。

- 後方互換を維持した機能追加
- 既存機能の機能改良
- バグ修正
- セキュリティ修正
- ドキュメント更新
- テスト追加、検証修正
- 既存仕様を変えない内部整理
- CI/CD、開発環境、リリース手順の修正

## 7. 安定版バージョンの更新条件

安定版バージョンは、リリースポリシーに基づき、安定版として切り出すことが承認された場合のみ更新する。

main への merge、作業ブランチの完了、開発版バージョンの更新、タスク完了は、それ自体では安定版バージョンの更新を意味しない。

安定版リリース後に不具合が見つかった場合も、既存の安定版番号を書き換えたり、tag を付け替えたりしてはならない。不具合修正は新しい開発版バージョンとして積み上げ、リリース条件を満たした時点で新しい安定版バージョンとして切り出す。
