# ドキュメント憲章

**位置づけ**: 2類ドキュメント憲章
**責務**: ドキュメント体系、責務境界、開発計画、フェーズ計画、改訂単位
**ステータス**: 初期策定

---

## 1. 基本方針

本憲章は、本リポジトリにおけるドキュメント体系、責務境界、改訂単位、開発計画の扱いを定義する。

`AGENTS.md` は、作業者が必ず従う絶対原則、禁止事項、優先順位、承認条件、作業手順の上位ルールを定義する1類ルールブックである。

`AGENTS.md` は、2類ポリシーおよび3類マスター仕様書の上位に位置し、ポリシーや仕様書の内容を統制する。ただし、2類ポリシーの責務範囲に属する詳細条件、判定基準、運用方針を重複して詳細定義する文書ではない。

2類ポリシーは、`AGENTS.md` に従う下位文書として、ドキュメント体系、開発プロセス、技術要件、バージョン、リリース、テスト、ライセンス等の責務別方針、判定条件、運用手順を定義する。

2類ポリシーは、`AGENTS.md` の絶対原則に違反してはならない。`AGENTS.md` と2類ポリシーが矛盾する場合は、`AGENTS.md` を正とし、2類ポリシーを修正して整合させる。

`AGENTS.md` に置くべき内容は、全作業に適用される絶対原則、禁止事項、優先順位、承認義務、上位参照順序に限る。責務別の詳細な条件、判定基準、手順、例外管理は、該当する2類ポリシーを正本として定義する。

`AGENTS.md` と2類ポリシーの役割を混同してはならない。

過去に、2類ポリシーで定義すべき詳細条件、読了対象、判定基準、運用手順を `AGENTS.md` に重複して詳細記載した誤りがあった。この誤りを繰り返してはならない。

`AGENTS.md` を改訂する場合は、追加内容が絶対原則、禁止事項、優先順位、承認義務、上位参照順序に該当するかを必ず確認する。該当しない詳細条件、判定基準、運用手順、例外管理は `AGENTS.md` に追加せず、該当する2類ポリシーへ記載する。

2類ポリシーを改訂する場合は、`AGENTS.md` の絶対原則に従いつつ、責務別の詳細を自分の責務範囲で定義する。2類ポリシーの詳細を `AGENTS.md` に戻す、または `AGENTS.md` と2類ポリシーへ同じ詳細を二重管理することを禁止する。

役割混同を発見した場合は、上位下位の関係だけで判断せず、まず内容の責務を判定する。全作業に適用される絶対原則は `AGENTS.md` へ、責務別の詳細条件と運用手順は該当する2類ポリシーへ移し、両者の整合を取る。

すべてのドキュメント作業、開発作業、検証作業、Git 操作、Pull Request 作成、レビュー対応、リリース判断では、必ず最初に1類ルールブックである `AGENTS.md` を確認する。

`AGENTS.md` の確認だけで読了義務を満たしたと扱ってはならない。

すべての作業では、`AGENTS.md` を最初に確認した後、最上位ドキュメント全体を読む。

最上位ドキュメント全体とは、最低限以下を指す。

- `AGENTS.md`
- 2類ドキュメント群の全ファイル
- 3類マスター仕様書群の全ファイル
- `docs/plans/DEVELOPMENT_PLAN.md`
- `docs/plans/MASTER_IMPLEMENTATION_FEATURE_CANDIDATES.md`
- `README.md`

最上位ドキュメント全体を読み終えるまで、ドキュメント体系、責務境界、フェーズ状態、仕様根拠、実装対象、対象外、検証範囲、リリース可否、Git 操作について判断してはならない。

未読、部分読了、過去に読んだ記憶、前回作業時の要約だけを根拠にして、読了義務を満たしたと扱ってはならない。

2類責務別ポリシーは、本憲章を参照し、各ポリシーの責務範囲、重複禁止、参照関係、改訂単位を本憲章に従って管理する。

ドキュメントは、1類ルールブック、2類ドキュメント群、3類マスター仕様書、マスター開発計画、マスター実装機能候補リストの責務を混同してはならない。

ドキュメント整合性は、1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画、マスター実装機能候補リスト、README、実装、テスト、検証導線、バージョン表記、Pull Request 説明を含む全体へ適用する。特定のドキュメント、特定のフェーズ、特定の作業だけに限定して扱ってはならない。

## 2. 開発計画の基本方針

正式な開発計画は、マスター開発計画である `docs/plans/DEVELOPMENT_PLAN.md` で管理する。

マスター開発計画は、3類マスター仕様書に基づいて策定する。開発計画は仕様そのものを決める文書ではなく、3類マスター仕様書に定義された仕様を、フェーズ、順序、検証、完了条件へ落とし込むための文書である。

マスター開発計画の改訂は、フェーズ単位で行う。複数フェーズへ影響する変更であっても、影響範囲、実装対象、対象外、検証範囲、完了条件をフェーズごとに分けて記録する。

フェーズに紐づかない計画変更を、実装対象、検証範囲、リリース判定へ直接反映してはならない。共通方針を変更する場合も、その変更がどのフェーズに影響するかを明記する。

各フェーズでは、必ずドキュメント等の整合性向上を行う。

これは任意の品質改善ではなく、フェーズ単位で実施する必須ルールであり、ドキュメント憲章上のポリシーである。

各フェーズの完了条件には、リポジトリ全体の整合性確認と整合性向上を必ず含める。

リポジトリ整合性確認では、最低限以下の整合を確認する。

- 1類ルールブック
- 2類ポリシー
- 3類マスター仕様書
- マスター開発計画
- マスター実装機能候補リスト
- 実装とデータベース schema
- テストと検証導線
- バージョン表記
- README
- Pull Request の説明

上記に矛盾または古い表記が残る場合、補正が完了するまでフェーズを完了扱いにしてはならない。

リポジトリ整合性が取れていない状態で、次のフェーズに進んではならない。

次フェーズへ移行する前に、前フェーズのドキュメント、仕様、計画、ポリシー、実装、テスト、検証導線、バージョン表記、README、Pull Request 説明の整合性向上を完了していなければならない。

## 3. フェーズ計画の必須項目

各フェーズ計画には、最低限以下を定義する。

- フェーズ名
- フェーズの目的
- 実装対象機能
- 実装対象外機能
- 依存する3類マスター仕様書
- 対応する基準バージョン
- 必須検証項目
- 完了条件
- リリース可否判定
- リポジトリ整合性確認
- ドキュメント等の整合性向上

## 4. 実装着手条件

フェーズ実装に着手するには、以下をすべて満たさなければならない。

- `AGENTS.md` を確認している。
- 2類ドキュメント群を全て読了している。
- 3類マスター仕様書群を全て読了している。
- マスター開発計画、マスター実装機能候補リスト、README を読了している。
- 対象フェーズが `docs/plans/DEVELOPMENT_PLAN.md` に定義されている。
- 対象フェーズの実装対象、対象外、検証範囲、基準バージョンが明確である。
- 対象フェーズに対応する3類マスター仕様書が整備されている。
- 前フェーズのリポジトリ整合性確認とドキュメント等の整合性向上が完了している。
- ソースコード実装作業についてユーザー承認を得ている。

## 5. フェーズ変更

フェーズ途中で実装範囲を変更する場合は、以下を必須とする。

1. 変更理由を明確にする。
2. `docs/plans/DEVELOPMENT_PLAN.md` を更新する。
3. 影響する3類マスター仕様書を更新する。
4. 必要に応じて2類責務別ポリシーを更新する。
5. ユーザー承認を得る。
6. 承認済み範囲のみ変更する。

## 6. 開発計画の改訂単位

マスター開発計画を改訂する場合は、以下の単位で記録する。

- 対象フェーズ
- 対象フェーズの基準バージョン
- 改訂理由
- 実装対象への影響
- 対象外への影響
- 検証範囲への影響
- 完了条件への影響
- 上位ドキュメントとの整合

改訂内容が全フェーズ共通の方針である場合も、改訂履歴には共通方針であることを明記し、必要に応じて各フェーズの該当項目へ反映する。
