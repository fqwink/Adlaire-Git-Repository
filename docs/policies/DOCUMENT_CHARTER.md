# ドキュメント憲章

**位置づけ**: 2類ドキュメント憲章
**責務**: ドキュメント体系、責務境界、タスク管理、整合性改訂単位
**ステータス**: 初期策定

---

## 1. 基本方針

本憲章は、本リポジトリにおけるドキュメント体系、責務境界、改訂単位、タスク管理の扱いを定義する。

`docs/DOCUMENT_INDEX.md` は、本リポジトリの参照索引である。参照対象の一覧、読了対象、各ドキュメントの役割確認に用いる。

`docs/DOCUMENT_INDEX.md` は、1類ルールブック、2類ポリシー、3類マスター仕様書、タスク管理ファイルの代替ではない。索引と正本が矛盾する場合は、正本を優先し、索引を修正して整合させる。

`docs/tpl-governance/` は、AdlaireGroup 関連プロジェクト、プロダクトへ展開する共通ガバナンス雛形の正本である。

`docs/tpl-governance/` 配下は、本プロジェクト固有の正本ドキュメントではなく、AdlaireGroup 共通方針を他プロジェクトへ展開するための正本雛形として管理する。

`AGENTS.md` は、作業者が必ず従う絶対原則、禁止事項、優先順位、承認条件、作業手順の上位ルールを定義する1類ルールブックである。

`AGENTS.md` は、2類ポリシーおよび3類マスター仕様書の上位に位置し、ポリシーや仕様書の内容を統制する。ただし、2類ポリシーの責務範囲に属する詳細条件、判定基準、運用方針を重複して詳細定義する文書ではない。

2類ポリシーは、`AGENTS.md` に従う下位文書として、ドキュメント体系、開発プロセス、技術要件、バージョン、リリース、テスト、ライセンス等の責務別方針、判定条件、運用手順を定義する。

2類ポリシーは、`AGENTS.md` の絶対原則に違反してはならない。`AGENTS.md` と2類ポリシーが矛盾する場合は、`AGENTS.md` を正とし、2類ポリシーを修正して整合させる。

`AGENTS.md` に置くべき内容は、全作業に適用される絶対原則、禁止事項、優先順位、承認義務、上位参照順序に限る。責務別の詳細な条件、判定基準、手順、例外管理は、該当する2類ポリシーを正本として定義する。

`AGENTS.md` と2類ポリシーの役割を混同してはならない。

過去に、2類ポリシーで定義すべき詳細条件、読了対象、判定基準、運用手順を `AGENTS.md` に重複して詳細記載した誤りがあった。この誤りを繰り返してはならない。

`AGENTS.md` を改訂する場合は、追加内容が絶対原則、禁止事項、優先順位、承認義務、上位参照順序に該当するかを必ず確認する。該当しない詳細条件、判定基準、運用手順、例外管理は `AGENTS.md` に追加せず、該当する2類ポリシーへ記載する。

2類ポリシーを改訂する場合は、`AGENTS.md` の絶対原則に従いつつ、責務別の詳細を自分の責務範囲で定義する。2類ポリシーの詳細を `AGENTS.md` に戻す、または `AGENTS.md` と2類ポリシーへ同じ詳細を二重管理することを禁止する。

役割混同を発見した場合は、上位下位の関係だけで判断せず、まず内容の責務を判定する。全作業に適用される絶対原則は `AGENTS.md` へ、責務別の詳細条件と運用手順は該当する2類ポリシーへ移し、両者の整合を取る。

変更を加える作業では、承認工程を省略してはならない。

エージェントは、変更前に必ず変更対象、変更理由、変更案、影響範囲、検証方法を提示し、ユーザー承認を得なければならない。提示または提案を行わずに、ユーザー発言を承認済み変更範囲として扱ってはならない。

承認後に限り、承認済み範囲の編集、検証、承認済み範囲だけの stage、commit、push、Pull Request 作成または更新を自動実行してよい。

承認済み範囲を超える変更、方針の意味変更、ソースコード実装、依存関係・技術採用・バージョン固定、Pull Request merge、`main` 反映、作業ブランチ削除、破壊的 Git 操作は、必ず別途承認を得る。

承認工程の詳細条件、自動化してよい範囲、別承認が必要な範囲は、2類ポリシーに詳細記載する。まず `AGENTS.md` に絶対原則を記載し、その後、該当する2類ポリシーに詳細を記載して整合させる。

すべてのドキュメント作業、開発作業、検証作業、Git 操作、Pull Request 作成、レビュー対応、リリース判断では、必ず最初に1類ルールブックである `AGENTS.md` を確認する。

`AGENTS.md` の確認だけで読了義務を満たしたと扱ってはならない。

すべての作業では、`AGENTS.md` を最初に確認した後、最上位ドキュメント全体を読む。

最上位ドキュメント全体を読む工程では、直前作業の Pull Request merge 状態、作業ブランチのクローズ状態、ローカルとリモートの整合性を同時に確認する。

最上位ドキュメント全体とは、最低限以下を指す。

- `AGENTS.md`
- `docs/DOCUMENT_INDEX.md`
- 2類ドキュメント群の全ファイル
- 3類マスター仕様書群の全ファイル
- `docs/tasks/TASK_MANAGEMENT.md`
- `README.md`

最上位ドキュメント全体を読み終えるまで、ドキュメント体系、責務境界、タスク状態、仕様根拠、実装対象、対象外、検証範囲、リリース可否、Git 操作について判断してはならない。

未読、部分読了、過去に読んだ記憶、前回作業時の要約だけを根拠にして、読了義務を満たしたと扱ってはならない。

2類責務別ポリシーは、本憲章を参照し、各ポリシーの責務範囲、重複禁止、参照関係、改訂単位を本憲章に従って管理する。

ドキュメントは、1類ルールブック、2類ドキュメント群、3類マスター仕様書、タスク管理ファイルの責務を混同してはならない。

ドキュメント整合性は、1類ルールブック、2類ポリシー、3類マスター仕様書、タスク管理ファイル、README、実装、テスト、検証導線、バージョン表記、Pull Request 説明を含む全体へ適用する。特定のドキュメント、特定のタスク、特定の作業だけに限定して扱ってはならない。

採用技術、固定バージョン、ライセンス、デプロイ方式、データ保存、依存関係、セキュリティ要件は、AdlaireGroup 共通方針として扱う。

プロジェクト名、プロダクト名、仕様書名、配置先、サーバ名、ドメイン、タスク管理、実装対象機能は、共通方針を破らない範囲で各プロジェクトが具体化する。

本プロジェクトのドキュメント変更が AdlaireGroup 共通方針に該当する場合は、`docs/tpl-governance/` の更新要否を必ず判定し、該当する場合は同一変更範囲で雛形も整合させる。

## 1.1 ガバナンス正本の境界

ガバナンス文書は、以下の境界で管理する。

| 区分 | 対象 | 役割 |
|---|---|---|
| 本リポジトリ運用正本 | `AGENTS.md`、`docs/policies/`、`docs/specs/`、`docs/tasks/` | Adlaire Git Repository の作業、仕様、タスク、運用を決定する |
| 参照索引 | `docs/DOCUMENT_INDEX.md` | 正本への参照順序、読了対象、役割を整理する |
| 利用者向け要約 | `README.md` | 利用者、作業者向けに正本への導線と概要を示す |
| 共通ガバナンス雛形正本 | `docs/tpl-governance/` | AdlaireGroup 関連プロジェクト、プロダクトへ展開する共通方針の雛形を管理する |
| 個別具体化枠 | `docs/tpl-governance/policy-slots/` | 共通方針を破らず、各プロジェクトで固有値を具体化する枠を示す |

本リポジトリ運用正本と共通ガバナンス雛形正本は、どちらも正本であるが対象が異なる。本リポジトリ運用正本は Adlaire Git Repository に適用し、共通ガバナンス雛形正本は AdlaireGroup 関連プロジェクト、プロダクトへ展開するために適用する。

共通雛形に、Adlaire Git Repository 固有の機能仕様、固有タスク、固有配置パス、固有ドメイン、固有サーバ名を直接固定してはならない。必要な場合は、placeholder または policy slot の具体化項目として表現する。

## 1.2 ガバナンス更新フロー

ガバナンスを改良する場合は、以下の順で判断する。

1. 変更内容が絶対原則か、責務別ポリシーか、仕様か、タスク管理か、利用者向け要約かを判定する。
2. 正本となる文書を一つ決める。
3. 他文書へ同じ詳細条件を重複記載せず、必要に応じて参照または要約に留める。
4. AdlaireGroup 共通方針に該当するかを判定する。
5. 共通方針なら `docs/tpl-governance/` へ同一変更範囲で反映する。
6. プロジェクト固有なら `docs/tpl-governance/` へ反映せず、Pull Request 説明に理由を記載する。
7. 正本、索引、README、テンプレート、Pull Request 説明の整合性を確認する。

判断が微妙な場合は、共通化できる原則とプロジェクト固有値を分離する。共通原則は共通雛形へ、固有値は本リポジトリ運用正本または各プロジェクトの個別具体化枠へ記載する。

## 2. タスク管理の基本方針

今後の作業管理は、`docs/tasks/TASK_MANAGEMENT.md` で管理する。

タスク管理ファイルは、廃止した旧計画ファイルおよび旧候補リストファイルの後継であり、未策定、未改訂、未実装の作業だけを管理する。

タスク管理ファイルは仕様書ではなく、実装承認でもない。仕様判断は3類マスター仕様書を正本とし、実施判断はユーザー承認を正とする。

タスク管理ファイルでは、タスクを `策定タスク` と `実装タスク` に分ける。

策定タスクは、未策定または未改訂のルール、ポリシー、仕様、運用条件、検証条件を整理するタスクである。

実装タスクは、3類マスター仕様書と承認済み方針に基づく未実装のソースコード、検証、運用導線を実装するタスクである。

策定タスクが未完了で仕様または方針が不明確な場合、該当する実装タスクへ進んではならない。

完了したタスクは、タスク管理ファイルから削除する。完了履歴は Git commit、Pull Request、tag、release notes、必要な仕様書改訂で確認する。

変更作業ごとに、必ずドキュメント等の整合性向上を行う。

これは任意の品質改善ではなく、変更作業ごとに実施する必須ルールであり、ドキュメント憲章上のポリシーである。

各変更作業の完了条件には、リポジトリ全体の整合性確認と整合性向上を必ず含める。

リポジトリ整合性確認では、最低限以下の整合を確認する。

- 1類ルールブック
- 2類ポリシー
- 3類マスター仕様書
- タスク管理ファイル
- 実装とデータベース schema
- テストと検証導線
- バージョン表記
- README
- Pull Request の説明

上記に矛盾または古い表記が残る場合、補正が完了するまで変更作業を完了扱いにしてはならない。

リポジトリ整合性が取れていない状態で、次のタスクに進んではならない。

次タスクへ移行する前に、直前タスクのドキュメント、仕様、ポリシー、タスク管理、実装、テスト、検証導線、バージョン表記、README、Pull Request 説明の整合性向上を完了していなければならない。

## 3. タスク管理の必須項目

タスク管理ファイルには、最低限以下を定義する。

- タスク分類
- タスクID
- タスク名
- 根拠
- 状態
- 完了後削除方針

タスク管理ファイルへ完了済みタスクを履歴目的で残してはならない。

## 4. 実装着手条件

実装に着手するには、以下をすべて満たさなければならない。

- `AGENTS.md` を確認している。
- 2類ドキュメント群を全て読了している。
- 3類マスター仕様書群を全て読了している。
- タスク管理ファイル、README を読了している。
- 対象タスクが `docs/tasks/TASK_MANAGEMENT.md` に定義されている。
- 対象タスクの実装対象、対象外、検証範囲が明確である。
- 対象タスクに対応する3類マスター仕様書が整備されている。
- 直前タスクのリポジトリ整合性確認とドキュメント等の整合性向上が完了している。
- ソースコード実装作業についてユーザー承認を得ている。

## 5. タスク変更

タスク途中で実装範囲を変更する場合は、以下を必須とする。

1. 変更理由を明確にする。
2. `docs/tasks/TASK_MANAGEMENT.md` を更新する。
3. 影響する3類マスター仕様書を更新する。
4. 必要に応じて2類責務別ポリシーを更新する。
5. ユーザー承認を得る。
6. 承認済み範囲のみ変更する。

## 6. タスク管理の改訂単位

タスク管理ファイルを改訂する場合は、以下の単位で記録する。

- 対象タスク
- タスク分類
- 改訂理由
- 実装対象への影響
- 対象外への影響
- 検証範囲への影響
- 完了条件への影響
- 上位ドキュメントとの整合

改訂内容が全タスク共通の方針である場合も、共通方針であることを明記し、必要に応じて関連タスクへ反映する。
