# テストポリシー

**位置づけ**: 2類責務別ポリシー
**責務**: 意味のあるテスト、テストピラミッド、テスト追加・削除判断
**ステータス**: 初期策定

---

## 1. 基本思想

テストは手段であり、目的は仕様が壊れていないという確信を得ることである。

本プロジェクトでは、意味のあるテストのみを作成・維持する。意味のないテストを作成してはならない。

## 2. 意味のあるテスト

意味のあるテストとは、以下の条件を満たすテストである。

- 失敗した時に、何が壊れたのかを説明できる。
- 失敗した瞬間に、どの仕様または振る舞いが壊れたのかを特定できる。
- 実装を変更しても、外から見た仕様が同じであれば生き残る。
- 内部構造、内部実装、私的な関数分割、内部の一時変数に依存しない。
- 外から見た振る舞い、入力、出力、副作用、権限、永続化結果、エラー応答を検証する。
- 3類マスター仕様書またはタスク管理ファイルのどの要求を守るためのテストか説明できる。

## 3. テストピラミッド

テスト構成は、以下のピラミッドを原則とする。

| 層 | 方針 |
|---|---|
| 土台 | 大量の高速なユニットテスト |
| 中間 | 主要境界を検証する統合テスト |
| 頂点 | 少数のエンドツーエンドテスト |

## 4. 冗長なテストの削除

確信にも説明にも寄与しない冗長なテストは削除する。

テストを削除する場合は、同じ確信をより良いテストが提供している、仕様から削除された振る舞いを検証している、または内部実装に過剰依存していて仕様保護に寄与していないことを確認する。

## 5. 実行環境

テストは、ホストOS上の固定採用バージョン Go で実行する。

Docker を用いる検証、テスト、ビルド、binary 生成は、Adlaire Pipeline 経由の対象として扱う。

Adlaire Pipeline 経由で Docker を用いる場合も、意味のあるテストの条件、テストピラミッド、冗長なテストの削除方針は同じく適用する。
