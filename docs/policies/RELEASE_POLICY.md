# リリースポリシー

**位置づけ**: 2類責務別ポリシー
**責務**: 安定版リリース、リリース対象、リリース禁止条件
**ステータス**: GitHub Releases 現行配置 / Go single binary 成果物方針

---

## 1. リリース対象

本プロジェクトで正式にリリース対象とするものは、安定版リリースのみとする。

開発版バージョン `v.0.N` は、開発・検証・文書改訂段階の番号であり、正式な安定版リリース対象ではない。

安定版リリースとして扱うバージョンは、バージョンポリシーに基づき `v.X.Y` 形式とする。`X` は安定版リリースの通し番号、`Y` は切り出し時点の開発版バージョン `v.0.N` の `N` である。

main への merge、作業ブランチの完了、開発版バージョンの更新、フェーズ完了は、それ自体では安定版リリースを意味しない。

安定版リリースフェーズは、Phase 7、Phase 17、Phase 27 のような 7系フェーズをデフォルト方針とする。

5系フェーズは設計・デザイン改良、仕様整理のためのフェーズとし、安定版リリースフェーズまたは補助的なリリース判定フェーズとして扱わない。

6系フェーズは、大規模なバグ修正とドキュメント整合性向上をデフォルト方針とする安定版リリース準備フェーズとする。必要に応じて移行準備と検証強化も行う。6系フェーズ自体は安定版リリースフェーズとして扱わない。

Phase 9 は、ユーザー承認に基づく安定版判定フェーズとして扱う。Phase 19、Phase 29 のような後続9系フェーズは、自動的な安定版判定フェーズまたは補助的なリリース判定フェーズとして扱わない。後続9系フェーズで安定版判定を行う場合は、マスター開発計画と2類ポリシーに明記し、ユーザー承認を得る。

## 2. リリース禁止条件

以下に該当する場合、リリースしてはならない。

- 既知のバグが残っている。
- セキュリティ要件の検証が未完了である。
- 主要仕様に対する意味のあるテストまたは代替検証による確信を説明できない。
- 3類マスター仕様書と実装が矛盾している。
- バージョン表記がバージョンポリシーに従っていない。
- ライセンス方針が未確認である。
- 安定版リリースとして判定されていない。
- リリース提案、配置先、成果物、検証方法、承認範囲が未提示である。
- ユーザー承認を得ていない。

## 3. 安定版以外の扱い

以下は正式リリース対象に含めない。

- 開発中バージョン
- 検証版
- 内部確認版
- 試験的実装
- 仕様未確定の暫定版
- 既知バグが残る版

安定版リリース後に不具合が見つかった場合も、公開済みの安定版バージョン、tag、release notes、成果物を番号上の同一リリースとして差し替えてはならない。不具合修正は新しい開発版バージョンとして積み上げ、リリース禁止条件に該当しないことを確認したうえで、新しい安定版バージョンとして切り出す。

## 4. リリース提案

リリース作業を行う前に、必ずリリース提案を提示し、ユーザー承認を得る。

リリース提案には、最低限以下を含める。

- 対象バージョン
- 対象フェーズ
- リリース理由
- リリース成果物
- リリース配置先
- 検証方法
- 承認後に自動実行する範囲

リリース提案を提示せずに、tag 作成、GitHub Releases 作成、成果物配置、release notes 公開、`main` 反映を行ってはならない。

## 5. リリース配置

リリース成果物の現行配置先は GitHub Releases とする。

GitHub Releases には、リリースごとの成果物、release notes、必要な checksum、manifest を配置する方針とする。

Adlaire Pipeline は、リリース基盤システムと自動実行基盤システムを担う機能として、Adlaire Git Repository 本体内部の CI/CD Domain に統合する方針とする。将来的な機能群は、`Adlaire Pipeline Release`、`Adlaire Pipeline Runner`、`Adlaire Pipeline Artifact`、`Adlaire Pipeline Deploy`、`Adlaire Pipeline Audit` とする。Adlaire Pipeline が仕様確定、実装、検証、安定運用できるまで、GitHub Releases は現行の正式リリース配置元として維持する。

将来的に Adlaire Pipeline をリリース成果物、release notes、checksum、manifest、release 履歴の正本にする場合は、リリース配置先の変更として扱い、1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画を改訂し、ユーザー承認を得る。

Linux 向け Go single binary を安定版リリース成果物とする場合は、ARM64 と x86_64 の2種類を標準配置対象とする。

Adlaire 公式 SDK は、Adlaire Git Repository 本体へ同梱せず、独立リリース対象とする。SDK のリポジトリ分離は現時点では未定とし、当面は現行リポジトリ内の `sdk/` で管理する。SDK 配布方式は現行リポジトリで扱い、リポジトリ分離時は分離先リポジトリで扱う。SDK リリース開始フェーズはマスター開発計画と本ポリシーに従い、リリース作業ごとにユーザー承認を得る。SDK のリリースは Adlaire Git Repository 本体の安定版リリースを自動的に意味せず、本体の安定版リリースも SDK のリリースを自動的に意味しない。

リポジトリ内に、変更履歴、リリース履歴、release notes 元資料、リリース配置記録、リリース用 manifest、リリース用 checksum を履歴ファイルとして保持してはならない。

大きなバイナリ成果物をリポジトリへ継続的に直接配置してはならない。大きな成果物は GitHub Releases へ配置する。

現行のリリース履歴の正本は GitHub Releases とする。リリースごとの release notes、成果物、checksum、manifest は GitHub Releases 側に配置し、リポジトリ内の `docs/releases/` または `releases/` へ履歴ファイルとして配置しない。

デプロイ、バックアップ、検証で生成される operational な manifest、checksum、log は、変更履歴ファイルではなく運用記録として扱う。これらの保存先、保護対象、バックアップ方針は `docs/policies/DEPLOYMENT_POLICY.md` を正本とする。

## 6. リリース自動化

リリース作業は、承認工程を省略しない範囲で自動化を推奨する。

本番サーバ環境へのデプロイ、デプロイ前後の検証、バックアップ、ロールバックは `docs/policies/DEPLOYMENT_POLICY.md` を正本とする。リリース自動化とデプロイ自動化を同時に扱う場合も、承認対象、成果物、検証範囲、失敗時対応を分けて提示する。

Adlaire Pipeline は、将来のリリース自動化とデプロイ自動化の正本候補であり、Adlaire Git Repository 本体内部の CI/CD Domain として扱う。`Adlaire Pipeline Release` は release notes、checksum、manifest、release 履歴を扱う候補とし、`Adlaire Pipeline Artifact` は成果物管理を扱う候補とする。`Adlaire Pipeline Runner` は検証、ビルド、定期実行、手動実行、実行制御を扱う候補とし、`Adlaire Pipeline Deploy` はデプロイ反映、切り替え、ロールバック準備を扱う候補とする。`Adlaire Pipeline Audit` は実行履歴・監査を扱う候補とする。これらは同一の CI/CD Domain 内の機能群として扱い、独立した機能ドメインへ細分化しない。Adlaire Pipeline の開発言語は Go 採用方針とする。データベース、依存関係、実行基盤は未定とし、別途ユーザー承認を得るまで固定してはならない。

ユーザー承認後に限り、以下を自動実行してよい。

- Git tag 作成
- GitHub Releases 作成
- 成果物アップロード
- checksum 生成
- manifest 生成
- release notes 反映
- Pull Request 更新

自動化する場合も、対象バージョン、対象フェーズ、配置先、成果物、検証方法、自動実行範囲を事前に提示し、ユーザー承認を得なければならない。

## 7. 別承認が必要なリリース作業

以下は、リリース自動化の対象としてまとめて扱わず、必ず別途承認を得る。

- 初回安定版リリース判定
- 安定版リリースとしての公開判断
- `main` 反映
- Pull Request merge
- リモートまたはローカル作業ブランチ削除
- リリース配置先の新規決定または変更
- 公開済みリリースの削除
- 公開済み tag の削除または付け替え
