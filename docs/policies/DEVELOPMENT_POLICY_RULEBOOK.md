# 開発ポリシールールブック

本ドキュメントは、Auris / Adlaire Git Repository における **2類ポリシー** である。

本ドキュメントは `AGENTS.md` の下位に位置し、3類マスター仕様書より上位に位置する。開発プロセス、バージョニング、ライセンス、リリース判定、依存関係、品質管理に関する方針は、本ドキュメントに従う。

---

## 1. 基本原則

- 1類ルールブックである `AGENTS.md` に違反してはならない。
- 3類マスター仕様書は仕様の正本であり、実装内容はマスター仕様書に基づく。
- ソースコード実装作業は、ユーザー承認を得てから着手する。
- 変更した場合は、承認済みの変更範囲だけを stage し、必ずコミットまで行う。
- `main` への直接 push は禁止し、必ず Pull Request 経由で取り込む。
- Pull Request がマージされた作業ブランチは、自動的に閉じる方針とする。

## 2. 開発計画ポリシー

### 2.1 フェーズ単位の実装計画

本プロジェクトの開発計画は、フェーズ単位で策定する。

正式な開発計画は `docs/plans/DEVELOPMENT_PLAN.md` で管理する。

各フェーズでは、3類マスター仕様書に基づいて、実装対象、対象外、検証範囲、リリース判定条件、対応バージョンを明確にする。

ソースコード実装作業に着手する前に、対象フェーズが `docs/plans/DEVELOPMENT_PLAN.md` に定義されていなければならない。

### 2.2 フェーズ計画の必須項目

各フェーズ計画には、最低限以下を定義する。

- フェーズ名
- フェーズの目的
- 実装対象機能
- 実装対象外機能
- 依存する3類マスター仕様書
- 対応する基準バージョン
- 必須検証項目
- 完了条件
- リリース可否判定

### 2.3 フェーズ別バージョン割当

各フェーズには、必ず `v.{Major}.{Minor}` 形式の基準バージョンを割り当てる。

`Major` は安定版リリース世代と対応させる。フェーズが大きく進み、運用前提または機能範囲が変わる場合は、次の `Major` へ進める。

`Minor` はプロジェクト全体の累積変更番号であり、フェーズ変更時または `Major` 更新時もリセットしてはならない。

フェーズ計画で定義した基準バージョンは、実装着手時点の計画値である。フェーズ内でドキュメント更新、検証追加、バグ修正、機能改良が発生した場合は、`Minor` を累積で進める。

例:

```text
Phase 0: v.0.1
Phase 1: v.1.2
Phase 2: v.2.3
Phase 3: v.3.4
```

### 2.4 フェーズ実装順序

フェーズ内の実装は、以下の順序を原則とする。

1. 仕様整理
2. セキュリティ・認証・認可に関わる基盤
3. データ永続化
4. コア機能
5. Web UI
6. テスト・検証
7. リリース判定

3類マスター仕様書またはユーザー指示で優先順位が定義されている場合は、そちらを優先する。

### 2.5 フェーズ変更

フェーズ途中で実装範囲を変更する場合は、以下を必須とする。

1. 変更理由を明確にする
2. `docs/plans/DEVELOPMENT_PLAN.md` を更新する
3. 影響する3類マスター仕様書を更新する
4. 必要に応じて本ポリシーを更新する
5. ユーザー承認を得る
6. 承認済み範囲のみ変更する

### 2.6 実装着手条件

フェーズ実装に着手するには、以下をすべて満たさなければならない。

- `AGENTS.md` を確認している。
- 本ポリシーを確認している。
- 対象フェーズが `docs/plans/DEVELOPMENT_PLAN.md` に定義されている。
- 対象フェーズの実装対象、対象外、検証範囲、基準バージョンが明確である。
- 対象フェーズに対応する3類マスター仕様書が整備されている。
- ソースコード実装作業についてユーザー承認を得ている。

## 3. バージョンポリシー

### 3.1 バージョン表記

本プロジェクトの正式バージョンは、以下の形式で表記する。

```text
v.{Major}.{Minor}
```

例:

```text
v.0.1
v.1.12
v.2.23
v.12.150
```

### 3.2 各要素の意味

| 要素 | 意味 |
|---|---|
| `Major` | 安定版リリースの世代 |
| `Minor` | プロジェクト全体で累積する変更番号 |

`Major` と `Minor` は 0 以上の整数とし、桁数制限は設けない。

### 3.3 累積方式とリセット禁止

本プロジェクトのバージョンは累積方式とする。

`Minor` はプロジェクト全体で累積し、`Major` 更新時もリセットしてはならない。

禁止例:

```text
v.1.12 -> v.2.0
```

許可例:

```text
v.1.12 -> v.2.13
v.2.23 -> v.3.24
v.12.150 -> v.13.151
```

### 3.4 Major の更新条件

`Major` は安定版リリースの扱いを表す。

以下のいずれかに該当し、新しい安定版リリースとして扱う場合、`Major` を更新する。

- 既存データ、API、Git 操作、認証、権限管理に非互換変更が発生する
- システムアーキテクチャを大きく変更する
- Phase が大きく進み、運用前提が変わる
- セキュリティ方針またはライセンス方針に重大な変更がある
- 安定版として利用者・運用者に明確な区切りを示す必要がある
- 3類マスター仕様書で Major 更新が必要と定義された

`Major` を更新する場合も、`Minor` は累積値を維持し、次の番号へ進める。

例:

```text
v.1.12 -> v.2.13
v.12.150 -> v.13.151
```

### 3.5 Minor の更新条件

以下のいずれかに該当する場合、`Minor` を更新する。

- 後方互換を維持した機能追加
- 既存機能の明確な機能改良
- 新しい設定項目、運用機能、管理機能の追加
- 3類マスター仕様書の範囲内での仕様拡張
- バグ修正
- セキュリティ修正
- ドキュメント更新
- テスト追加、検証修正
- 既存仕様を変えない内部整理
- CI/CD、開発環境、リリース手順の修正

例:

```text
v.0.1 -> v.0.2
v.1.11 -> v.1.12
v.2.22 -> v.2.23
v.12.149 -> v.12.150
```

### 3.6 初期バージョン

正式な実装開始前の初期整備段階は、以下を基準バージョンとする。

```text
v.0.1
```

Phase 1 の最小実装が完了し、Git 基本操作、認証、Repository CRUD、最小 Web UI、基本テストが成立した時点で、`v.1.x` 系への昇格を検討する。

### 3.7 バージョン更新手順

バージョン更新は以下の順序で行う。

1. 変更種別を判定する
2. `Major` / `Minor` のどちらを更新するか決定する
3. 3類マスター仕様書の該当箇所を更新する
4. 必要に応じて本ポリシーを更新する
5. 実装またはドキュメント変更を行う
6. 検証結果を記録する
7. PR を作成する

## 4. ライセンスポリシー

### 4.1 現時点のライセンス

本プロジェクトのライセンスは、現時点では **クローズドライセンス** とする。

### 4.2 クローズドライセンス方針

以下を禁止する。

- 無断複製
- 無断再配布
- 無断改変物の公開
- 無断商用利用
- 無断 OSS 化
- ライセンス未承認状態での第三者提供

### 4.3 権利帰属

本プロジェクトに含まれるソースコード、ドキュメント、設計、仕様、名称、関連成果物の権利は、正式な権利者またはプロジェクト管理主体に帰属する。

権利帰属の詳細は、3類マスター仕様書または別途定める契約・社内規程を優先する。

### 4.4 外部公開

本プロジェクトを外部公開する場合、事前に以下を完了しなければならない。

- ライセンス方針の再承認
- 公開範囲の決定
- 秘密情報、認証情報、内部情報の除去
- 依存関係とライセンスの確認
- 3類マスター仕様書への公開条件記載

### 4.5 ライセンス変更

クローズドライセンスから別ライセンスへ変更する場合は、Major 更新候補とする。

ライセンス変更時は、以下を必須とする。

1. ユーザー承認
2. 1類ルールブックとの整合確認
3. 本ポリシーの更新
4. 3類マスター仕様書の更新
5. 必要に応じた `LICENSE` または `LICENSE.md` の作成

## 5. リリース判定ポリシー

### 5.1 リリース対象

本プロジェクトで正式にリリース対象とするものは、**安定版リリースのみ** とする。

安定版リリースとは、3類マスター仕様書に定義された対象範囲を満たし、主要検証を完了し、既知バグが残っておらず、運用・利用に供してよいと判断されたバージョンである。

以下は正式リリース対象に含めない。

- 開発中バージョン
- 検証版
- 内部確認版
- 試験的実装
- 仕様未確定の暫定版
- 既知バグが残る版

安定版として扱うリリースは、Major バージョンの扱いと整合させる。

### 5.2 リリース禁止条件

以下に該当する場合、リリースしてはならない。

- 既知のバグが残っている
- セキュリティ要件の検証が未完了
- 認証、認可、Git 操作、Repository CRUD、データ永続化の主要検証が未完了
- 3類マスター仕様書と実装が矛盾している
- バージョン表記が本ポリシーに従っていない
- ライセンス方針が未確認である
- 安定版リリースとして判定されていない

---

## 6. ポリシー変更手順

本ドキュメントを変更する場合は、以下を守る。

1. 1類ルールブックに違反しないことを確認する
2. 変更理由を明確にする
3. 影響する3類マスター仕様書を確認する
4. ユーザー承認を得る
5. 承認済み範囲のみ変更する
6. コミットする
7. PR 経由で `main` に取り込む
