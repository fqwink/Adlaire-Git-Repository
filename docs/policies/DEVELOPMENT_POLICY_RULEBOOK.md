# 開発ポリシールールブック

本ドキュメントは、Auris / Adlaire Git Repository における **2類ポリシー** である。

本ドキュメントは `AGENTS.md` の下位に位置し、3類マスター仕様書より上位に位置する。

本ドキュメントは、2類ドキュメント群の総則である。ドキュメント体系と責務境界はドキュメント憲章に分離し、開発プロセス、バージョニング、ライセンス、リリース判定、テスト、依存関係、品質管理に関する詳細方針は、責務ベースで独立した責務別ポリシーに分離する。

2類ドキュメント群は以下とする。

| 優先順位 | ポリシー | 責務 |
|---:|---|---|
| 1 | `docs/policies/DEVELOPMENT_POLICY_RULEBOOK.md` | 2類ドキュメント群の総則、共通原則、参照順序、変更手順 |
| 2 | `docs/policies/DOCUMENT_CHARTER.md` | ドキュメント憲章。ドキュメント体系、責務境界、開発計画、フェーズ単位の改訂方針 |
| 3 | `docs/policies/TECHNICAL_REQUIREMENTS_POLICY.md` | 採用技術、ランタイム、依存関係、固定採用バージョン、技術承認 |
| 4 | `docs/policies/VERSION_POLICY.md` | バージョン表記、累積方式、Major / Minor 更新条件 |
| 5 | `docs/policies/RELEASE_POLICY.md` | 安定版リリース、リリース対象、リリース禁止条件 |
| 6 | `docs/policies/DEPLOYMENT_POLICY.md` | デプロイ、運用基盤、本番サーバ反映、バックアップ、検証、ロールバック |
| 7 | `docs/policies/TEST_POLICY.md` | 意味のあるテスト、テストピラミッド、テスト追加・削除判断 |
| 8 | `docs/policies/LICENSE_POLICY.md` | クローズドライセンス、権利帰属、外部公開、ライセンス変更 |

各責務別ポリシーは、自分の責務範囲における正本である。他責務の詳細を重複定義せず、必要な場合は該当ポリシーを参照する。

各責務別ポリシーは、`docs/policies/DOCUMENT_CHARTER.md` を参照し、ドキュメント体系、責務境界、改訂単位に従う。

参照対象の一覧、読了対象、各ドキュメントの役割は、`docs/DOCUMENT_INDEX.md` を索引として確認する。`docs/DOCUMENT_INDEX.md` は参照索引であり、1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画の代替ではない。

## 0.1 ルールブックとポリシーの役割

`AGENTS.md` は、作業者が必ず従う絶対原則、禁止事項、優先順位、承認条件、作業手順の上位ルールを定義する1類ルールブックである。

`AGENTS.md` は、2類ポリシーおよび3類マスター仕様書の上位に位置し、ポリシーや仕様書の内容を統制する。ただし、2類ポリシーの責務範囲に属する詳細条件、判定基準、運用方針を重複して詳細定義する文書ではない。

2類ポリシーは、`AGENTS.md` に従う下位文書として、ドキュメント体系、開発プロセス、技術要件、バージョン、リリース、テスト、ライセンス等の責務別方針、判定条件、運用手順を定義する。

2類ポリシーは、`AGENTS.md` の絶対原則に違反してはならない。`AGENTS.md` と2類ポリシーが矛盾する場合は、`AGENTS.md` を正とし、2類ポリシーを修正して整合させる。

`AGENTS.md` に置くべき内容は、全作業に適用される絶対原則、禁止事項、優先順位、承認義務、上位参照順序に限る。責務別の詳細な条件、判定基準、手順、例外管理は、該当する2類ポリシーを正本として定義する。

### 0.1.1 役割混同の再発防止

`AGENTS.md` と2類ポリシーの役割を混同してはならない。

過去に、2類ポリシーで定義すべき詳細条件、読了対象、判定基準、運用手順を `AGENTS.md` に重複して詳細記載した誤りがあった。この誤りを繰り返してはならない。

`AGENTS.md` を改訂する場合は、追加内容が絶対原則、禁止事項、優先順位、承認義務、上位参照順序に該当するかを必ず確認する。該当しない詳細条件、判定基準、運用手順、例外管理は `AGENTS.md` に追加せず、該当する2類ポリシーへ記載する。

2類ポリシーを改訂する場合は、`AGENTS.md` の絶対原則に従いつつ、責務別の詳細を自分の責務範囲で定義する。2類ポリシーの詳細を `AGENTS.md` に戻す、または `AGENTS.md` と2類ポリシーへ同じ詳細を二重管理することを禁止する。

役割混同を発見した場合は、上位下位の関係だけで判断せず、まず内容の責務を判定する。全作業に適用される絶対原則は `AGENTS.md` へ、責務別の詳細条件と運用手順は該当する2類ポリシーへ移し、両者の整合を取る。

### 0.1.2 承認工程省略の再発防止

変更を加える作業では、承認工程を省略してはならない。

エージェントは、変更前に必ず変更対象、変更理由、変更案、影響範囲、検証方法を提示し、ユーザー承認を得なければならない。提示または提案を行わずに、ユーザー発言を承認済み変更範囲として扱ってはならない。

承認後に限り、承認済み範囲の編集、検証、承認済み範囲だけの stage、commit、push、Pull Request 作成または更新を自動実行してよい。

承認済み範囲を超える変更、方針の意味変更、ソースコード実装、依存関係・技術採用・バージョン固定、Pull Request merge、`main` 反映、作業ブランチ削除、破壊的 Git 操作は、必ず別途承認を得る。

承認工程の詳細条件、自動化してよい範囲、別承認が必要な範囲は、2類ポリシーに詳細記載する。まず `AGENTS.md` に絶対原則を記載し、その後、該当する2類ポリシーに詳細を記載して整合させる。

#### 承認前提示の必須項目

エージェントは、変更前に最低限以下を提示する。

- 変更対象ファイルまたは変更対象領域
- 変更理由
- 変更案または追加・修正する文言の要旨
- 1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画、実装、Git 運用への影響範囲
- 実施予定の検証方法
- 承認後に自動実行する範囲

上記を提示せずに編集、削除、移動、生成、stage、commit、push、Pull Request 作成または更新を行ってはならない。

#### 承認範囲の扱い

ユーザー承認は、提示した変更対象、変更理由、変更案、影響範囲、検証方法、自動実行範囲に限定して有効とする。

「やれ」「明記しろ」「改訂しろ」等の指示があっても、エージェントが変更前提示を行っていない場合は、承認工程を完了した扱いにしてはならない。

作業中に変更範囲の拡大、方針の意味変更、対象ファイルの追加、検証方法の変更、影響範囲の拡大が必要になった場合は、作業を止め、再提示して再承認を得る。

#### 承認後に自動実行してよい範囲

ユーザーが提示内容を承認した場合、エージェントは承認済み範囲に限り、以下を自動実行してよい。

- 承認済みファイルの編集
- 差分確認
- `git diff --check`
- 作業内容に応じた検証
- 承認済み範囲だけの stage
- commit
- 作業ブランチへの push
- 既存 Pull Request 更新
- Pull Request が存在しない場合の Pull Request 作成

自動実行した場合も、最終報告で変更内容、検証結果、commit、Pull Request を報告しなければならない。

#### 別承認が必要な範囲

以下は、承認後の自動実行範囲に含めてはならず、必ず別途承認を得る。

- 承認済み範囲を超える変更
- `AGENTS.md` の絶対原則の意味変更
- 2類ポリシーの責務変更
- 3類マスター仕様書の仕様変更
- ソースコード実装
- テストコードの追加・変更・削除
- 依存関係、技術採用、採用バージョン、固定バージョンの変更
- Pull Request merge
- `main` 反映
- リモートまたはローカル作業ブランチ削除
- 破壊的 Git 操作

## 1. 基本原則

- `AGENTS.md` 自体が、本リポジトリにおける絶対原則である。
- すべての作業において、必ず最初に1類ルールブックである `AGENTS.md` を読む。`AGENTS.md` を読まずに、調査、設計、ドキュメント改訂、実装、検証、Git 操作、Pull Request 作成、レビュー対応、リリース判断へ着手してはならない。
- `AGENTS.md` を読んだだけで作業判断に必要な確認を完了したと扱ってはならない。
- 作業前の読了対象、読了条件、未読時の禁止事項は `docs/policies/DOCUMENT_CHARTER.md` を正本とする。
- 読了義務を満たすまで、調査結果の断定、方針判断、フェーズ移行、ドキュメント改訂、ソースコード実装、テスト変更、検証スクリプト変更、Git 操作、Pull Request 作成を開始してはならない。
- 1類ルールブックである `AGENTS.md` に違反してはならない。
- 3類マスター仕様書は仕様の正本であり、実装内容はマスター仕様書に基づく。
- ソースコード実装作業は、ユーザー承認を得てから着手する。
- 開発言語、ランタイム、データベース、Git、外部コマンド、外部ライブラリ、フレームワーク、採用バージョン、固定バージョン、更新方針は、ユーザーが決定する。
- エージェントは候補提示、比較、調査、リスク整理、推奨案の提示にとどめ、ユーザー承認なしに採用決定、バージョン固定、方針確定、実装反映をしてはならない。
- Adlaire Git Repository 本体は、Go を標準開発言語とし、Go single binary を正本成果物とする。Deno + TypeScript は、本リポジトリ本体の開発言語として終了方針とする。Adlaire Pipeline は Go 採用方針とする。AdlaireGroup 関連プロジェクト、プロダクトでは、Deno + TypeScript と Go 単体の2系統を有効な開発言語選択肢として扱い、プロジェクトごとにユーザー承認を得て選定する。
- Adlaire Git Repository は、UI を差し替え可能にするため、ヘッドレスアーキテクチャ設計思想を採用する。UI は Adlaire Git Repository 本体に固定せず、本体は特定 UI に依存しない。HTML / CSS / Vanilla JavaScript で構成され、静的コンテンツ専用サーバー等で動作するフロントエンドや、モバイルアプリ等のクライアントを可能にする。UI および外部システムとの接続は、原則として Adlaire 公式 SDK を通じて行う。
- Adlaire 公式 SDK は、Adlaire Git Repository 本体ではなくクライアント接続境界として扱う。SDK は TypeScript で実装し、Vanilla JavaScript から利用できる JavaScript を生成する方針とする。SDK は本体へ同梱せず独立リリース対象とし、当面は現行リポジトリ内の `sdk/` で管理する。SDK の生成方式は Deno runtime とし、配布方式は現行リポジトリで扱い、リポジトリ分離時は分離先リポジトリで扱う。SDK 固定採用バージョンと SDK リリース開始フェーズは2類ポリシーとマスター開発計画に従う。
- 本番サーバ運用、デプロイ、運用基盤では、Go single binary 形式を標準化対象とする。Go single binary を正本成果物とし、Docker は Adlaire Git Repository 本体の直接標準運用選択肢ではなく、Adlaire Pipeline 経由で生成、管理、配布、利用する対象とする。保護対象 data 側は host filesystem を正本として system 側から分離する。詳細は `docs/policies/TECHNICAL_REQUIREMENTS_POLICY.md` と `docs/policies/DEPLOYMENT_POLICY.md` を正本とする。
- 本番サーバ環境へのデプロイは、承認工程を省かず、バックアップ、検証、ロールバック前提を含めて自動化を標準とし、詳細は `docs/policies/DEPLOYMENT_POLICY.md` を正本とする。
- Go 採用プロジェクトでは Go 標準ライブラリを優先し、Deno + TypeScript 採用プロジェクトでは Deno 標準ライブラリ（`jsr:@std/*`）を優先する。ただし、個別モジュールまたは Go module の採用はユーザー承認なしに行ってはならない。
- Go module、JSR レジストリの公開ライブラリ、その他外部ライブラリは、必要最小限の外部ライブラリ例外採用として扱う。
- JSR レジストリの公開ライブラリを採用する場合は、Node.js ランタイム環境が存在しない前提で、Deno runtime だけで動作することを必須条件とする。
- JSR レジストリの公開ライブラリであっても、npm 互換、`npm:` specifier、`package.json`、`node_modules`、Node.js runtime、npm ecosystem への依存を前提とするものは例外なく採用禁止とする。
- クローズド資産は JSR へ公開してはならず、クローズドな Adlaire 内製 Deno package の中長期配布基盤は Adlaire 内製 Deno Module Registry とする。Adlaire 内製 Deno Module Registry は、Adlaire Git Repository 本体へ早期実装する方針とする。
- npm registry 互換レジストリは Node.js / npm ecosystem リスクと衝突するため標準採用しない。
- npm 依存は、実行時、開発時、検証時、ビルド時のいずれでも採用してはならない。
- 変更した場合は、承認済みの変更範囲だけを stage し、必ずコミットまで行う。
- `main` への直接 push は禁止し、必ず Pull Request 経由で取り込む。
- Pull Request がマージされた作業ブランチは、自動的に閉じる方針とする。
- Pull Request の確認とマージ作業はユーザーが行う。エージェントは、Pull Request 作成後、ユーザーからマージ完了通知がない場合でも、後続作業の最上位ドキュメント読了工程と同時に Pull Request のマージ完了、作業ブランチのクローズ状態、ローカルとリモートの整合性を確認する。
- ドキュメント整合性は、1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画、マスター実装機能候補リスト、README、実装、テスト、検証導線、バージョン表記、Pull Request 説明を含む全体へ適用する。一部の文書、特定フェーズ、特定作業だけに限定して扱ってはならない。
- フェーズ単位で、必ずドキュメント等の整合性向上を行う。これは任意の品質改善ではなく、本リポジトリのルールであり、2類ポリシーである。
- 各フェーズの完了前に、リポジトリ全体の整合性確認と整合性向上を必ず行い、矛盾または古い表記が残る場合は補正完了までフェーズを完了扱いにしてはならない。
- リポジトリ整合性が取れていない状態で、次のフェーズに進んではならない。

## 3. バージョンポリシー

### 3.1 バージョン表記

本プロジェクトの正式バージョンは、以下の形式で表記する。

```text
v.{Major}.{Minor}
```

未安定版の例:

```text
v.0.1
v.0.12
```

安定版リリース系列の例:

```text
v.1.13
v.2.23
v.12.150
```

### 3.2 各要素の意味

| 要素 | 意味 |
|---|---|
| `Major` | 安定版リリース系列。初回安定版前は `0` |
| `Minor` | プロジェクト全体で累積する変更番号 |

`Major` と `Minor` は 0 以上の整数とし、桁数制限は設けない。

### 3.3 累積方式とリセット禁止

本プロジェクトのバージョンは累積方式とする。

フェーズ番号は累積方式とし、安定版リリース後もリセットしてはならない。

初回安定版リリース前の正式バージョンは、`v.0.{Minor}` として扱う。安定版未リリース中は、Phase が進んでも `Major` を `0` のまま維持する。

`Major` は安定版リリース系列として扱い、初回安定版リリースで `1` へ進める。

`Minor` はプロジェクト全体で累積し、`Major` 更新時またはフェーズ変更時もリセットしてはならない。

禁止例:

```text
v.1.12 -> v.2.0
v.5.20 -> v.6.1
```

安定版未リリース中の禁止例:

```text
v.0.12 -> v.1.13
```

許可例:

```text
v.0.12 -> v.0.13
v.1.24 -> v.1.25
v.1.150 -> v.2.151
```

初回安定版リリースとして承認された場合の許可例:

```text
v.0.23 -> v.1.24
```

### 3.4 Major の更新条件

`Major` は安定版リリース系列を表す。

以下のいずれかに該当し、新しい安定版リリース系列として扱う場合、`Major` を更新する。

- 既存データ、API、Git 操作、認証、権限管理に非互換変更が発生し、安定版系列を分ける必要がある
- システムアーキテクチャを大きく変更し、安定版系列を分ける必要がある
- Phase が大きく進み、安定版リリース系列として運用前提が変わる
- セキュリティ方針またはライセンス方針に重大な変更がある
- 7系フェーズに到達し、安定版として利用者・運用者に明確な区切りを示す必要がある
- Phase 9 または後続9系フェーズに到達し、ユーザー承認に基づいて安定版リリース判定を行う必要がある
- 3類マスター仕様書で Major 更新が必要と定義された

`Major` を更新する場合も、`Minor` は累積値を維持し、次の番号へ進める。

`Major` が `0` の間は、安定版未リリースの開発・検証段階である。

`Major` が `1` 以上のバージョンは、安定版リリース系列として扱う。

例:

```text
v.0.23 -> v.1.24
v.12.150 -> v.13.151
```

### 3.5 Minor の更新条件

以下のいずれかに該当する場合、`Minor` を更新する。

- 後方互換を維持した機能追加
- 既存機能の明確な機能改良
- 新しい設定項目、運用機能、管理機能の追加
- 3類マスター仕様書の範囲内での仕様拡張
- バグ修正
- セキュリティ修正
- ドキュメント更新
- テスト追加、検証修正
- 既存仕様を変えない内部整理
- CI/CD、開発環境、リリース手順の修正

例:

```text
v.0.1 -> v.0.2
v.1.11 -> v.1.12
v.2.22 -> v.2.23
v.12.149 -> v.12.150
```

### 3.6 初期バージョン

正式な実装開始前の初期整備段階は、以下を基準バージョンとする。

```text
v.0.1
```

Phase 1 の最小実装が完了しても、安定版リリース判定を行うまでは `v.0.x` 系を維持する。

ただし、Phase 1 は安定版リリースフェーズではない。Phase 1 の完了は開発検証段階の完了であり、安定版リリース判定ではない。

### 3.7 バージョン更新手順

バージョン更新は以下の順序で行う。

1. 変更種別を判定する
2. `Major` / `Minor` のどちらを更新するか決定する
3. 3類マスター仕様書の該当箇所を更新する
4. 必要に応じて本ポリシーを更新する
5. 実装またはドキュメント変更を行う
6. 検証結果を記録する
7. PR を作成する

### 3.8 Pull Request 作成後の確認とブランチクローズ

変更後は、リモート、ローカルの状態に関係なく、必ず Pull Request を作成する。

Pull Request の確認とマージ作業はユーザーが行う。エージェントは、Pull Request merge を自分で行ってはならない。

エージェントは、Pull Request 作成後、ユーザーからマージ完了通知がない場合でも、後続作業の開始時に最上位ドキュメントを読む工程と同時に以下を確認する。

- 対象 Pull Request が merge 済みか
- merge 済み Pull Request のリモート作業ブランチが閉じられているか
- ローカル作業ブランチが残っていないか
- リモート追跡参照に stale branch が残っていないか
- ローカル `main` と GitHub の `main` が同一 commit を指しているか

対象 Pull Request が merge 済みであることを確認した場合、エージェントはユーザーからの追加通知を待たず、リモート、ローカルの両方で作業ブランチのクローズ状態を確認し、必要なローカルブランチ削除、リモート追跡参照の prune、ローカル `main` の同期、整合性確認を実施する。

作業ブランチ削除は、merge 済み Pull Request に紐づく作業ブランチに限定する。別作業のブランチ、未 merge のブランチ、用途不明のブランチを削除してはならない。

## 5. リリース判定ポリシー

### 5.1 リリース対象

本プロジェクトで正式にリリース対象とするものは、**安定版リリースのみ** とする。

安定版リリースフェーズは、Phase 7、Phase 17、Phase 27 のような 7系フェーズをデフォルト方針とする。

5系フェーズは設計・デザイン改良、仕様整理のためのフェーズとし、安定版リリースフェーズまたは補助的なリリース判定フェーズとして扱わない。

6系フェーズは、大規模なバグ修正とドキュメント整合性向上をデフォルト方針とする安定版リリース準備フェーズとする。必要に応じて移行準備と検証強化も行う。6系フェーズ自体は安定版リリースフェーズとして扱わない。

Phase 9 は、ユーザー承認に基づく安定版判定フェーズとして扱う。Phase 19、Phase 29 のような後続9系フェーズは、自動的な安定版判定フェーズまたは補助的なリリース判定フェーズとして扱わない。後続9系フェーズで安定版判定を行う場合は、マスター開発計画と2類ポリシーに明記し、ユーザー承認を得る。

7系フェーズでも、安定版リリースとは自動的な公開を意味しない。安定版リリース判定条件を満たさない場合はリリースしてはならない。

Phase 1、Phase 2、Phase 3、Phase 4、Phase 5、Phase 6、Phase 8 は、開発、検証、統合、改善、準備のためのフェーズであり、安定版リリース対象ではない。Phase 9 は安定版判定フェーズとして扱う。

安定版リリースとは、3類マスター仕様書に定義された対象範囲を満たし、主要検証を完了し、既知バグが残っておらず、運用・利用に供してよいと判断されたバージョンである。

以下は正式リリース対象に含めない。

- 開発中バージョン
- 検証版
- 内部確認版
- 試験的実装
- 仕様未確定の暫定版
- 既知バグが残る版

安定版として扱うリリースは、Major バージョンの扱いと整合させる。

安定版リリースフェーズ以外の成果物を、安定版、安定版候補、正式リリース候補として扱ってはならない。

### 5.2 リリース禁止条件

以下に該当する場合、リリースしてはならない。

- 既知のバグが残っている
- セキュリティ要件の検証が未完了
- 認証、認可、Git 操作、Repository CRUD、データ永続化の主要検証が未完了
- 主要仕様に対する意味のあるテストまたは代替検証による確信を説明できない
- 3類マスター仕様書と実装が矛盾している
- バージョン表記が本ポリシーに従っていない
- ライセンス方針が未確認である
- 安定版リリースとして判定されていない

## 6. テストポリシー

### 6.1 基本思想

テストは手段であり、目的は仕様が壊れていないという確信を得ることである。

本プロジェクトでは、意味のあるテストのみを作成・維持する。意味のないテストを作成してはならない。

### 6.2 意味のあるテストの定義

意味のあるテストとは、以下の条件を満たすテストである。

- 失敗した時に、何が壊れたのかを説明できる。
- 失敗した瞬間に、どの仕様または振る舞いが壊れたのかを特定できる。
- 実装を変更しても、外から見た仕様が同じであれば生き残る。
- 内部構造、内部実装、私的な関数分割、内部の一時変数に依存しない。
- 外から見た振る舞い、入力、出力、副作用、権限、永続化結果、エラー応答を検証する。
- 3類マスター仕様書またはマスター開発計画のどの要求を守るためのテストか説明できる。
- 失敗時の情報が、修正判断、原因特定、リリース可否判断のいずれかに寄与する。

### 6.3 意味のないテストの禁止

以下のテストは意味のないテストとして禁止する。

- 失敗しても、どの仕様が壊れたのか分からないテスト。
- 実装の内部構造だけを固定し、外から見た振る舞いを検証しないテスト。
- 仕様が変わっていないのに、内部実装の変更だけで壊れるテスト。
- 既存テストと同じ確信しか与えない冗長なテスト。
- 成功してもリリース可否、品質判断、仕様説明に寄与しないテスト。
- テストのためだけに本番コードの責務や公開APIを歪めるテスト。

確信にも説明にも寄与しない冗長なテストは削除する。

### 6.4 テストピラミッド

テスト構成は、以下のピラミッドを原則とする。

| 層 | 方針 |
|---|---|
| 土台 | 大量の高速なユニットテスト |
| 中間 | 主要境界を検証する統合テスト |
| 頂点 | 少数のエンドツーエンドテスト |

ユニットテストは、仕様上意味のある入力と出力、エラー、境界条件を高速に検証する。

統合テストは、HTTP、認証、Git 操作、Database Gateway、libSQL 永続化、必要な移行元 SQLite データ確認など、複数の責務が接続されたときの振る舞いを検証する。

エンドツーエンドテストは、ユーザーまたは外部システムから見た重要なワークフローだけを少数に絞って検証する。

### 6.5 テスト対象の境界

テストは、原則として外から見た振る舞いを検証する。

検証対象は以下を優先する。

- 公開API
- HTTP endpoint
- CLI または Git protocol から見た結果
- Web UI のユーザー操作結果
- Database Gateway を経由した永続化結果
- 認証・認可の許可と拒否
- セキュリティ上の拒否動作
- 仕様で定義されたエラー応答

内部実装を直接検証する場合は、その内部境界が3類マスター仕様書または2類ポリシー上の正式な境界であり、外部振る舞いだけでは必要な確信を得られない場合に限る。

### 6.6 テスト追加・削除の判断

テストを追加する場合は、以下を確認する。

- どの仕様を守るためのテストか。
- 失敗した時に何を教えるテストか。
- 既存テストでは得られない確信を追加するか。
- 実装を変更しても仕様が同じなら壊れないか。
- テストの実行速度と保守負荷が、得られる確信に見合うか。

テストを削除する場合は、以下のいずれかに該当することを確認する。

- 同じ確信をより良いテストが提供している。
- 仕様から削除された振る舞いを検証している。
- 内部実装に過剰依存しており、仕様保護に寄与していない。
- 失敗しても原因特定やリリース判断に寄与しない。

### 6.7 リリース判定との関係

リリース判定では、テスト数ではなく、仕様に対する確信を評価する。

テストが多くても、意味のないテストが多い場合は品質保証とはみなさない。

テストが少なくても、主要仕様、主要リスク、主要ワークフローに対する確信を説明できる場合は、その説明をリリース判定材料とする。

本ドキュメントを変更する場合は、以下を守る。

1. 1類ルールブックに違反しないことを確認する
