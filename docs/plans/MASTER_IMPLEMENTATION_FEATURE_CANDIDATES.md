# マスター実装機能候補リスト

**位置づけ**: マスター実装機能候補リスト
**対象**: Auris / Adlaire Git Repository
**文書バージョン**: v.0.37
**ステータス**: 3類マスター仕様完成

---

## 1. 目的

本書は、今後の実装機能候補を種別ごとに整理するためのマスター実装機能候補リストである。

本書は、機能候補、優先候補、保留候補、候補選定理由を管理する。機能の正式仕様、実装範囲、Phase 割り当て、完了条件、検証範囲は、本書では確定しない。

保留候補は、保留扱いである。保留候補は、推奨候補フェーズ、正式な実装対象、実装予定、実装承認として扱ってはならない。保留候補を実装候補へ戻す場合は、保留解除理由、必要性、影響範囲を整理し、3類マスター仕様書、マスター開発計画、検証範囲へ反映し、ユーザー承認を得る。

本書は、1類ルールブックである `AGENTS.md`、2類ポリシー、3類マスター仕様書、マスター開発計画である `docs/plans/DEVELOPMENT_PLAN.md` に従う。

基本的な機能互換は GitHub 互換基準とし、オープンソース Git プロバイダーはサブの機能互換インスパイア対象として扱う。

ただし、GitHub や OSS Git プロバイダーに存在する機能であっても、現時点で不要な機能は実装対象から除外する。

本書はマスター実装機能候補リストであり、実装承認ではない。実装対象へ確定する場合は、3類マスター仕様書、マスター開発計画、検証範囲へ反映し、ユーザー承認を得る。

本書に記載された候補が3類マスター仕様書またはマスター開発計画に未反映である場合、その候補は未確定として扱う。候補リストと3類マスター仕様書またはマスター開発計画に重複記載がある場合、候補の分類と理由は本書、正式仕様と実装対象は3類マスター仕様書およびマスター開発計画を正とする。

本書と上位ドキュメントに矛盾がある場合は、上位ドキュメントを正とし、本書を修正する。

Phase 8 のマスター仕様完成後、本書は候補の分類、優先理由、保留理由のみを管理する。現行正本仕様、実装対象、対象外、検証範囲、完了条件は、3類マスター仕様書とマスター開発計画を正とする。

## 2. 選定基準

実装候補は、以下の基準で判断する。

- 内部向け Git ホスティング基盤として日常開発に必要か
- GitHub の基本的な機能互換として重要か
- Phase 2 以降の開発計画に収まるか
- セキュリティ、権限管理、監査に必要か
- 外部依存や運用負荷が過度に増えないか
- UI 互換ではなく、本プロジェクト独自 UI として実装できるか

## 3. フェーズ別優先実装候補

本章は、優先実装候補のみを優先度の高い順に、推奨候補フェーズ単位で整理する。

ここで示すフェーズは候補整理であり、正式な実装対象、対象外、検証範囲、完了条件を確定するものではない。正式な実装対象にする場合は、3類マスター仕様書と `docs/plans/DEVELOPMENT_PLAN.md` に反映し、ユーザー承認を得る。

保留候補は本章に含めない。保留候補は、後続フェーズの候補ではなく、保留解除とユーザー承認があるまで保留扱いとする。

フェーズ単位は累積方式で扱う。Phase 5 系は安定版リリース対象外のデザイン・仕様整理、Phase 6 系は大規模バグ修正・ドキュメント整合性向上をデフォルト方針とする安定版リリース準備、Phase 7 系はデフォルト安定版リリース判定として整理する。Phase 9 は安定版判定フェーズとし、後続9系は自動的な安定版判定フェーズまたは補助的なリリース判定フェーズとして扱わず、安定版判定を行う場合は2類ポリシーとマスター開発計画に明記し、ユーザー承認を得る。

### 3.1 Phase 2 推奨候補: 開発支援の中核

Phase 2 推奨候補は、日常開発の中核となるレビュー、課題管理、文書管理、連携口を優先する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Pull Request | 優先 | ブランチ間の変更提案、差分確認、マージ判断の中心機能であるため |
| 2 | Code Review | 優先 | Pull Request に対するコメント、承認、変更要求を扱う品質管理の基本機能であるため |
| 3 | Issue | 優先 | バグ、タスク、要望をリポジトリ単位で管理する基本機能であるため |
| 4 | Wiki | 優先 | リポジトリ単位の仕様、運用手順、補足資料を管理できるため |
| 5 | Webhook | 優先 | 外部通知、内部ツール連携、将来の自動化の土台になるため |
| 6 | REST API 基本機能 | 優先 | 内部ツールや運用スクリプトから利用できる基本連携口になるため |
| 7 | Release 管理 | 優先 | tag 名とリリースノートのメタデータ管理を整理でき、バージョン方針と相性がよいため |

### 3.2 Phase 2 補強候補: 運用品質

Phase 2 補強候補は、Phase 2 の中核候補を安全に運用するための補助機能として扱う。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 8 | Repository settings 拡張 | 優先 | visibility、default branch、保護設定など運用に必要な管理項目を扱うため |
| 9 | 権限管理強化 | 優先 | private repository、merge、Issue 編集、Wiki 編集などの操作制御に必要なため |
| 10 | 監査ログ拡張 | 優先 | 内部向け基盤として、誰が何をしたか追跡できることが重要であるため |

### 3.3 Phase 3 推奨候補: 組織・運用基盤と内製 Deno Module Registry

Phase 3 推奨候補は、Phase 2 までの開発支援機能を組織単位で運用し、Adlaire 内製 Deno package を本体内で配布するための最小基盤を優先する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Organizations 最小運用 | 優先 | 個人単位だけでなく組織単位でリポジトリ所有と権限管理を行うため |
| 2 | Teams 最小運用 | 優先 | 組織内の権限付与を個別ユーザー管理だけに依存しないため |
| 3 | Projects 最小運用 | 優先 | Issue と Pull Request を横断して作業単位を整理するため |
| 4 | Adlaire 内製 Deno Module Registry 最小実装 | 優先 | Adlaire 内製 Deno / TypeScript / ESM package を JSR へ公開せず、Node.js / npm ecosystem に依存せず、本体の認証・認可・監査と統合して配布する必要があるため |
| 5 | REST API 対象リソース拡張 | 優先 | Phase 3 の組織、チーム、プロジェクト、Registry 操作を内部ツールから扱うため |
| 6 | Webhook 対象イベント拡張 | 優先 | Phase 2 の基本 Webhook を、運用上必要なイベント範囲へ広げるため |
| 7 | 高度な監査ログ | 優先 | 組織、チーム、Registry、権限変更を追跡可能にするため |
| 8 | 運用自動化 | 優先 | 内部向け Git ホスティング基盤として日常運用の手戻りを減らすため |
| 9 | libSQL 標準DB化 | 優先 | libSQL を標準DBとし、SQLite 互換維持を行わないDB方針へ移行するため |

Adlaire 内製 Deno Module Registry の初期候補範囲は、package metadata、version 管理、module 登録、checksum、Deno native import / download endpoint、認証・認可、監査ログとする。

汎用 Package registry、npm registry 互換レジストリ、Container registry は本候補に含めない。

### 3.4 Phase 4 推奨候補: 統合・仕様整合・移行準備

Phase 4 推奨候補は、新規機能追加よりも、Phase 1 から Phase 3 までの成果を統合し、後続フェーズへ進むための整合性を高めることを優先する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Phase 1 から Phase 3 までの統合確認 | 優先 | Git 基本機能、開発支援機能、組織・Registry 機能の組み合わせを検証するため |
| 2 | 仕様整合 | 優先 | 1類ルールブック、2類ポリシー、3類マスター仕様書、マスター開発計画の矛盾を解消するため |
| 3 | 移行準備 | 優先 | SQLite / libSQL 移行可能性、バックアップ、復旧、ロールバックの前提を整理するため |
| 4 | 検証導線整理 | 優先 | 後続フェーズと安定版準備へ進むための確認手段を明確にするため |

### 3.5 Phase 5 推奨候補: デザイン関連改良・改修

Phase 5 推奨候補は、Web UI の使いやすさ、視認性、操作導線、表示品質を整えるためのデザイン・仕様整理候補とする。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Web UI 情報設計整理 | 優先 | Phase 1 から Phase 4 までに増えた機能を、利用者が迷わず扱える構成へ整理するため |
| 2 | 画面レイアウト改良 | 優先 | リポジトリ、Issue、Pull Request、Wiki、Release、Registry 関連画面の見通しを高めるため |
| 3 | 視覚表現統一 | 優先 | 色、余白、文字サイズ、状態表示を統一し、内部向け基盤としての利用品質を高めるため |
| 4 | 操作導線改良 | 優先 | 日常開発で頻繁に使う作成、確認、更新、レビュー、マージ等の操作を分かりやすくするため |
| 5 | アクセシビリティ・可読性改善 | 優先 | 長時間利用、権限状態、エラー状態、モバイル・デスクトップ表示で確実に読み取れる UI にするため |

Phase 5 のデザイン関連候補は、GitHub UI 互換ではなく、本プロジェクト独自 UI の改良・改修候補として扱う。外部フレームワーク採用候補として扱ってはならない。

Phase 5 は安定版リリース対象外である。

### 3.6 Phase 6 推奨候補: 安定版リリース準備

Phase 6 推奨候補は、大規模バグ修正とドキュメント整合性向上をデフォルト方針とし、Phase 7 の安定版リリース判定へ進むための準備に限定する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | 大規模バグ修正 | 優先 | 安定版判定前に既知バグを残さない状態へ近づけるため |
| 2 | ドキュメント整合性向上 | 優先 | 仕様、計画、ポリシー、実装、検証導線の矛盾をなくすため |
| 3 | 主要ワークフロー検証強化 | 優先 | Repository、PR、Issue、Wiki、Webhook、Release、Registry の振る舞いを確認するため |
| 4 | 移行・ロールバック手順整理 | 優先 | 安定版リリース前に復旧可能性を説明できる状態にするため |
| 5 | Phase 7 残課題整理 | 優先 | 安定版リリース判定で確認すべき論点を明確にするため |

Phase 6 は安定版リリース準備フェーズであり、安定版リリース対象外である。

### 3.7 Phase 7 推奨候補: デフォルト安定版リリース判定

Phase 7 推奨候補は、7系フェーズのデフォルト安定版リリース判定として、リリース可否を判断するための候補に限定する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | 安定版リリース判定 | 優先 | 7系フェーズをデフォルト安定版リリース判定として扱うため |
| 2 | リリースノート整理 | 優先 | 安定版として提供する内容、対象外、既知制約を説明するため |
| 3 | 最終リポジトリ整合性確認と整合性向上 | 優先 | 既知バグ、仕様矛盾、検証不足を確認し、次フェーズへ進む前に補正を完了するため |

### 3.8 Phase 8 / Phase 9 推奨候補: DB仕様完成と安定版判定

Phase 8 は DB 仕様完成フェーズとする。Phase 8.1 は本体整合性、Phase 8.5 は Adlaire Git Repository 本体とデータ領域の分割、Phase 8.7 は安定化を扱う。Phase 9 は安定版判定フェーズとする。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | DB仕様完成 | 優先 | libSQL 標準DB仕様、Database Gateway 境界、SQLite 互換維持なし方針、移行元 SQLite 取扱境界を実装判断可能な粒度へ整理するため |
| 2 | 本体整合性 | 優先 | DB 方針変更に合わせて本体仕様、計画、実装、検証導線を整合するため |
| 3 | システム分割 | 優先 | Adlaire Git Repository 本体とデータ領域を分割し、system 側と data 側の責務を明確にするため |
| 4 | 安定化 | 優先 | バグ修正、検証強化、ドキュメント整合性を行うため |
| 5 | 安定版判定 | 優先 | Phase 9 で安定版リリース可否を判断するため |

### 3.9 Phase 10 推奨候補: GitHub Releases 現行配置 / Adlaire Pipeline 付随システム候補整理

Phase 10 推奨候補は、現行リリース配置を GitHub Releases として整合し、Adlaire Pipeline を Release、Runner、Artifact、Deploy、Audit の将来機能群を持つ内製付随システム候補として整理することを優先する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | GitHub Releases 現行配置整理 | 優先 | Go single binary、release notes、checksum、manifest の現行配置先を明確にするため |
| 2 | リポジトリ内リリース履歴ファイル廃止維持 | 優先 | 変更履歴、release notes 元資料、リリース配置記録、リリース用 manifest、checksum をリポジトリへ保持しない方針を維持するため |
| 3 | 標準デプロイ雛形との責務整理 | 優先 | `scripts/deploy/` 配下の shell script を、GitHub Releases 配置済み成果物を本番サーバへ反映する補助導線として説明するため |
| 4 | Adlaire Pipeline 付随システム候補整理 | 優先 | `Adlaire Pipeline Release`、`Adlaire Pipeline Runner`、`Adlaire Pipeline Artifact`、`Adlaire Pipeline Deploy`、`Adlaire Pipeline Audit` を将来機能群として扱い、開発言語は Go 採用方針、実装、データベース、依存関係、実行基盤、本体統合は未定とするため |
| 5 | リポジトリ整合性確認 | 優先 | 1類、2類、3類、マスター開発計画、README、検証導線、PR説明から古いリリース配置方針を除去するため |

### 3.10 Phase 11 推奨候補: Go移行準備

Phase 11 推奨候補は、Adlaire Git Repository 本体を Go へ移行する前に、実装構成、固定採用バージョン、外部依存、検証導線、旧 Deno + TypeScript 資産の扱いを整理することを優先する。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Go 実装基盤整理 | 優先 | 本体を Go single binary 方針へ移すための構成、責務境界、起動導線を明確にするため |
| 2 | Go 固定採用バージョン候補整理 | 優先 | 最新安定版方針に基づき、ユーザー承認前に採用候補と検証方法を提示するため |
| 3 | 外部依存例外候補整理 | 優先 | Go module を含む外部ライブラリを必要最小限に抑え、採用前承認を徹底するため |
| 4 | 旧 Deno + TypeScript 資産整理 | 優先 | 本体終了方針に基づき、撤去対象、履歴保持対象、移行対象を混同しないため |
| 5 | Go 検証導線整理 | 優先 | `go fmt`、`go test`、`go build`、Linux ARM64 / x86_64 build の確認範囲を定義するため |
| 6 | ヘッドレスアーキテクチャ方針整理 | 優先 | UI を本体に固定せず、静的フロントエンドやモバイルアプリ等のクライアントを可能にし、Adlaire 公式 SDK 経由の接続方針を仕様へ反映するため |
| 7 | Docker の Adlaire Pipeline 経由方針整理 | 優先 | Docker を本体の直接標準運用選択肢ではなく、Adlaire Pipeline 経由で扱う方針へ整合するため |
| 8 | Adlaire 公式 SDK 仕様完成 | 優先 | SDK 専用の3類マスター仕様書を完成させ、SDK の公開境界、非責務、TypeScript 実装、Vanilla JavaScript 向け JavaScript 生成、本体非同梱、`sdk/` 管理、独立リリース、対象外、未確定範囲を、実装前に仕様へ固定するため |

## 4. 保留候補

保留候補は、保留扱いである。以下の機能は、保留解除とユーザー承認があるまで、推奨候補フェーズ、正式な実装対象、実装予定として扱ってはならない。

| 機能 | 種別 | 保留理由 |
|---|---|---|
| Organizations / Teams 本格運用 | 保留 | 権限設計が重く、まずは単純なユーザー、管理者、collaborator を優先するため |
| Projects 本格運用 | 保留 | Issue と Pull Request を横断する最小運用を確認してから、本格的なボード、ビュー、集計へ広げるべきであるため |
| Discussions | 保留 | Issue と Wiki で当面代替できるため |
| Webhook 本格拡張 | 保留 | Phase 3 の最小イベント拡張とは別に、配送キュー、再送、任意イベント発火まで広げるには運用結果が必要であるため |
| REST API 本格拡張 | 保留 | Phase 3 の対象リソース拡張とは別に、公開 API としての互換範囲を広げるには利用実績が必要であるため |
| Star / Watch | 保留 | 内部向け基盤では必須度が低く、通知設計と合わせて検討する必要があるため |
| Mirror repository | 保留 | 外部 Git サービス連携、認証情報管理、同期失敗時の扱いを整理する必要があるため |
| Code search | 保留 | 検索インデックス、性能、ストレージ設計が必要であり、小規模運用では後回しにできるため |
| Pages 相当 | 保留 | 静的ホスティング機能であり、Git ホスティング本体の優先度より低いため |
| CI / Actions 互換 | 保留 | 実行環境、権限分離、ジョブ隔離、セキュリティ設計が重いため |
| 汎用 Package registry | 保留 | 今後の計画として検討するが、Adlaire 内製 Deno Module Registry とは別機能であり、容量管理、認証、配布設計が重いため |
| Container registry | 保留 | Git ホスティング本体から外れ、ストレージ、セキュリティ、運用負荷が大きいため |
| Advanced Security | 保留 | 脆弱性DB、依存関係解析、スキャン基盤など外部依存や運用負荷が大きいため |

## 5. 採用見送り候補

採用見送り候補は、現時点の内部向け Git ホスティング基盤コアから外れるため、通常のフェーズ候補へ含めない。

| 優先順 | 機能 | 種別 | 理由 |
|---:|---|---|---|
| 1 | Copilot 相当 | 見送り | AI 機能であり、現時点の Git ホスティング基盤コアから外れるため |
| 2 | Federation | 見送り | 内部向け基盤では現時点の必要性が低く、運用モデルも大きく変わるため |
