# 開発ポリシールールブック

**対象**: `{PROJECT_NAME}`
**位置づけ**: 2類ポリシー総則
**責務**: 2類ポリシー群の総則、共通原則、参照順序、変更手順

---

## 1. 基本原則

- `AGENTS.md` は絶対原則である。
- 2類ポリシーは `AGENTS.md` に違反してはならない。
- 3類マスター仕様書は仕様の正本である。
- 変更を加える作業では、承認工程を省略してはならない。
- 本番サーバ環境へのデプロイは、承認工程を省かず、バックアップ、検証、ロールバック前提を含めて自動化を標準とする。
- `{PRIMARY_BRANCH}` への直接 push は禁止する。
- すべての変更は Pull Request 経由で取り込む。
- Pull Request の確認とマージ作業はユーザーが行う。作業者は、Pull Request 作成後、ユーザーからマージ完了通知がない場合でも、後続作業の最上位ドキュメント読了工程と同時に Pull Request のマージ完了、作業ブランチのクローズ状態、ローカルとリモートの整合性を確認する。
- 採用技術、固定バージョン、ライセンス、デプロイ方式、データ保存、依存関係、セキュリティ要件は AdlaireGroup 共通方針として扱う。
- 各プロジェクトは、共通方針を破らない範囲でプロジェクト固有値を具体化する。

## 3. 承認前提示

変更前に最低限以下を提示する。

- 変更対象
- 変更理由
- 変更案
- 影響範囲
- 検証方法
- 承認後に自動実行する範囲

提示なしに編集、削除、移動、生成、stage、commit、push、Pull Request 作成または更新を行ってはならない。

---

## 4. 承認後の自動化

ユーザー承認後に限り、承認済み範囲の編集、検証、stage、commit、push、Pull Request 作成または更新を自動実行してよい。

承認済み範囲を超える変更、Pull Request merge、`{PRIMARY_BRANCH}` 反映、作業ブランチ削除、破壊的 Git 操作は、必ず別途承認を得る。

---

## 5. Pull Request 作成後の確認

変更後は、リモート、ローカルの状態に関係なく、必ず Pull Request を作成する。

Pull Request の確認とマージ作業はユーザーが行う。作業者は Pull Request merge を自分で行ってはならない。

Pull Request 作成後、ユーザーからマージ完了通知がない場合でも、後続作業の開始時に最上位ドキュメントを読む工程と同時に以下を確認する。

- 対象 Pull Request が merge 済みか
- merge 済み Pull Request のリモート作業ブランチが閉じられているか
- ローカル作業ブランチが残っていないか
- リモート追跡参照に stale branch が残っていないか
- ローカル `{PRIMARY_BRANCH}` とリモート `{PRIMARY_BRANCH}` が整合しているか

対象 Pull Request が merge 済みの場合は、merge 済み Pull Request に紐づく作業ブランチに限り、作業ブランチのクローズとローカル・リモート整合性確認を行う。

---

## 6. 共通雛形更新判定

ルール、ポリシー、技術方針、ライセンス、デプロイ、データ、依存関係、セキュリティに関する変更を行う場合は、AdlaireGroup 共通方針に該当するかを判定する。

共通方針に該当する変更は、`docs/tpl-governance/` の雛形へ反映する。

プロジェクト固有仕様、固有機能、固有配置値、固有Phase計画は、共通雛形へ反映しない。
